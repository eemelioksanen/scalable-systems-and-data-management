# Local scaling experiments and design ablations (#11)

Measured on 17 and 18 November 2026. Every configuration ran three times with a full reset per repeat. These are **local parallel scaling** results on one host, not distributed scaling. #12 owns the multi-VM runs.

## Setup

- **Host:** Intel i7-11700K, 8 cores and 16 threads, 62 GiB of memory, NVMe disk. Docker 29.9.3 on Arch Linux (kernel 7.2.14), not under Podman. This is a different machine from the Mac VM used for the [baselines](../2026-10-12-baselines/README.md), so absolute numbers differ.
- **Code:** revision `0bbcfc9` (after #23's variants), with a clean tree recorded in every run.
- **Harness:** `bench/run.py --no-build`, using one image build for all runs.
- **Configs:** the configs are in [bench/configs/issue11/](../../../bench/configs/issue11/), generated by [make_configs.py](../../../scripts/validation/issue11/make_configs.py). [orchestrate.py](../../../scripts/validation/issue11/orchestrate.py) ran them, and [issue11-orchestrate.log](issue11-orchestrate.log) records every step.
- **Preloads:** the full week (289,116,808 rows), `--bounded`, with the D-38 finite-input baseline: a 64,265,001 ms bound and idleness off. `warmupS` was 15 s.
- **Live runs:** 08 November paced from 09:00, with a 1 s bound, 30 s idleness and a drain (D-38). `warmupS` was 25 s.
- **Default stack:** 1 TaskManager with one slot per parallel subtask, 8 `ticks` partitions, and one `*` subscription unless stated otherwise. Flink's memory is the image default, the same in every run. The viz service ran as part of the stack.
- **References (oracles):** each run is compared against an oracle computed from the same input:
  - `week`, admitting every event, for all preloads;
  - `week-carry-forward`, for the carry-forward variant;
  - `mon-bound1s` and `mon-bound60s`, for the whole-day live runs.

  [posthoc_correctness.py](../../../scripts/validation/issue11/posthoc_correctness.py) compared the runs `bench/run.py` refuses an oracle for (below).

### Running stacks side by side was tested and rejected

Before running anything in parallel, we checked whether two stacks pinned to separate CPU sets would influence each other. Lane A used cores 0–3 and 8–11, lane B cores 4–7 and 12–15. Each lane was all of one stack's services plus its comparison containers, and each lane's Prometheus kept only its own containers.

| Lane A, p4 full-week preload | Job M rec/s |
|---|---|
| alone | 4.67 ± 0.02 |
| with lane B running the same | 3.22 ± 0.18 (**−31%**) |

The tolerance was 3%. Pinning to separate cores does not isolate the two stacks: they still share the L3 cache, memory bandwidth and the disk. **Every run below ran alone on the whole host.** The side-by-side live check was stopped part-way, because it could not change the verdict. [issue11-calibration.json](issue11-calibration.json) has the verdict, and the calibration table in [tables.md](tables.md) has the per-run figures. Configs named `lane-*` kept that name but ran on the whole host.

## Results

[tables.md](tables.md) has the full tables: mean ± sample standard deviation over the COMPLETE repeats, and n. [runs.csv](runs.csv) has one row per run. Each group directory holds `summarize.py`'s `runs.csv`, `summary.csv`, `throughput.png` and `timeseries.png`. [resources.png](resources.png) shows TaskManager, Kafka and replayer CPU over one repeat of each scale run. `runs/<experiment>/<rK>/` keeps each run's `config.json` (stack, resources, hardware, versions, timestamps), `summary.json`, `replay.json` and comparison reports. The raw Prometheus series and exports stay in the ignored `bench/results/raw/`.

The **post-warm-up rate** is the sum of the source subtasks' read rates over the measurement interval. It excludes the ramp of roughly 15 s that the whole-job rate keeps (D-37).

### Correctness

- **All COMPLETE runs passed**, 0 EMA differences and 0 advisory differences. `lateTicks` was 0 in every run.
  - **Harness comparisons:** preload and whole-day live runs passed `bench/run.py`'s comparison.
  - **Post-hoc comparisons:** runs the harness refuses an oracle for were compared afterwards, 36 runs in all ([issue11-posthoc-correctness.json](issue11-posthoc-correctness.json)):
    - **Exchange subsets:** the week oracle cut to the subset's exchanges.
    - **Traders:** cut to the union of the subscribed symbols. This also checks what the subscription filter published.
    - **Live slices:** an oracle at a 1 s bound over Monday's first 3,000,000 data rows.
- **Failed runs:** 2 of 3 p16 runs on one TaskManager failed with `java.lang.OutOfMemoryError: Java heap space`. No other run failed.

### Parallelism and partitions (preload, whole host)

| p4, 16 part | 6.08 ± 0.06 | 6.26 ± 0.05 | 47.9 | 10.7 | | 44 | 1.05 | 1.10 |

| p16, 16 part, 1 TM × 16 | 3.36 (n = 1 of 3) | 3.49 | 86.4 | 11.9 | | 321 | 1.49 | 1.27 |
| p16, 16 part, 2 TM × 8 | 5.75 ± 0.11 | 6.47 ± 0.22 | 50.7 | 13.1 | 14.8 | 56 | 1.49 | 1.27 |

TM and host cores are means over the measurement interval. Garbage collection (GC) is summed over TaskManagers.

- **Scaling stops at p4.** Throughput rises 1.56× from p1 to p2 and 1.19× from p2 to p4. Above p4 it does not rise. From p4 the host is at 11.8 to 14.8 of its 16 logical CPUs, with only 8 physical cores, and the TaskManager uses 9.8 to 13 cores. The likeliest limit is the host's CPU. These runs did not separate that from the effect of SMT (simultaneous multithreading, two threads per core) or from memory bandwidth.
- **One TaskManager's default heap limits high parallelism.** At p16 on one TaskManager, the TaskManager spent 321 ms of every second in GC, and 2 of 3 repeats ran out of heap. Splitting the same 16 slots over two TaskManagers removed the failures and nearly doubled throughput: 5.75 against 3.36 M rec/s. At p8 the split gave +12% on 16 partitions. Its post-warm-up rate of 7.08 M rec/s is the highest of any configuration, but its whole-job rate (6.28) does not beat p4 on 8 partitions.
- **More partitions did not help.** 16 partitions read 6% (p4) and 9% (p8) slower than 8 at the same parallelism, beyond three standard deviations of the repeats. Per-subtask record counts are identical across partition counts. They depend only on the key hash, as #24 predicted, so the difference is in processing cost per partition.
- **Skew follows the hash, as predicted.** Source read skew was 1.05 at p4, 1.25 at p8 and 1.49 at p16. `q1-ema` read skew was 1.10, 1.15 and 1.27. These equal [predict_load.py](../../../bench/predict_load.py)'s values, so the real symbol skew costs at most 5% of balance at p4, but a quarter at p8 and half at p16.
- **State:** open windows peaked at 636 k per subtask at p1, 154 k at p4, 74 k at p8 and about 56–60 k at p16. Peak heap used, sampled every 5 s, stayed between 0.40 and 0.49 GiB in every scale run, whatever the parallelism. That is consistent with the default heap's capacity, and garbage collection grew instead. Checkpointed state bytes were not measured (see below).

### Bottlenecks

- **Replay is the end-to-end limit of every preload.** The single replayer sends 1.16 to 1.31 M rec/s on about 1.1 cores: 221 to 245 s for the week, against a 45 s job. Live, it reaches its limit between 300x and 1000x. At 1000x it achieved 980x, with send lag p50 9.1 s and p99 17.6 s, at about 1.04 M rec/s. At 300x its lag p99 was 193 ms.
- **Kafka:** the broker used 0.36 to 0.91 cores on average in every run. It is not a bottleneck.
- **Flink:** the `ticks` source is the busiest task in every baseline run, busy 0.85 to 0.94, against 0.32 to 0.48 for `q1-ema`. The binary-encoding variant (below), which removes CSV parsing from the source, is the largest single gain. That fits the source's parsing being the dominant cost.
- **Output:** the subscription filter and both sinks were busy 0.03 to 0.17. Not a bottleneck.
- **Saturation:** the job keeps up with every rate one replayer can offer. Live queueing p95 stayed 220 to 283 ms from 1x to 1000x. The job's own ceiling is the preload rate above.

### Traders (p4, 8 partitions)

Each trader has 20 symbols, drawn either uniformly over the 4,970 symbols with price events, or weighted by each symbol's price events ("skewed"). The draw uses a fixed seed (`make_configs.py`).

| Traders | Uniform: job M rec/s, output busy, results | Skewed: job M rec/s, output busy, results |
|---|---|---|
| 1 | 6.87 ± 0.03, 0.029, 7,731 | 6.83 ± 0.08, 0.028, 11,890 |
| 10 | 6.80 ± 0.07, 0.033, 71,639 | 6.80 ± 0.02, 0.034, 100,024 |
| 100 | 6.72 ± 0.05, 0.054, 602,694 | 6.69 ± 0.04, 0.053, 635,991 |

- **Cost follows published results, not trader count.** Going from 1 to 1000 traders costs 6% of throughput, and the output stage's busy ratio rises from 0.03 to 0.08. 1000 traders cost the same as one `*` subscription, which publishes about as much. The filter's lookup does not depend on the number of traders (D-17's two map reads).
- **Symbol skew in subscriptions makes no measurable difference** at equal trader counts.

### Design variants (p4, 8 partitions)

| Variant | Semantics | Job s | Job M rec/s | Post-warm-up M rec/s | Busy: source / q1 / output | Results | Reference |
|---|---|---|---|---|---|---|---|
| baseline (process, heap, CSV, Flink filter, skip) | | 44.7 ± 0.3 | 6.51 ± 0.05 | 6.77 ± 0.10 | 0.92 / 0.40 / 0.08 | 1,857,457 | week: pass |
| Window API | same | 45.0 ± 0.6 | 6.48 ± 0.09 | 6.76 ± 0.14 | 0.92 / 0.41 / 0.08 | 1,857,457 | week: pass |
| RocksDB state | same | 65.7 ± 3.1 | 4.47 ± 0.21 | 4.68 ± 0.13 | 0.49 / 0.92 / 0.04 | 1,857,457 | week: pass |
| binary `ticks` | same | 34.8 ± 0.6 | 8.39 ± 0.14 | 9.03 ± 0.23 | 0.81 / 0.52 / 0.10 | 1,857,457 | week: pass |
| early filtering in the replayer | same output | 21.6 ± 0.1 | 2.81 ± 0.02 * | 2.88 * | 0.87 / 0.72 / 0.17 | 1,857,457 | week: pass |
| carry-forward empty windows | **changed** | 49.4 ± 0.2 | 5.95 ± 0.04 | 6.14 ± 0.11 | 0.88 / 0.39 / 0.14 | 6,064,548 | week-carry-forward: pass |

\* Early filtering sends 59.7 M price events instead of 289 M rows, so its records per second count different records. Compare its durations instead:
- **job:** 21.6 s against 44.7 s (−52%);
- **replay:** 107 s against 228 s;
- **replay plus job:** 128 s against 272 s (−53%).

- **Window API:** no measurable difference from the process function.
- **RocksDB:** −31% throughput. It moves the bottleneck to `q1-ema`, which is busy 0.92, and it varies more between repeats (±3.1 s).
- **Binary encoding:** +29% job throughput, with the source busy 0.81 against 0.92. The replayer was 6% slower encoding it: 1.19 against 1.27 M rec/s.
- **Early filtering:** the largest end-to-end gain, because it shrinks both the replay and the job.
- **Carry-forward:** changes semantics. It emits 3.3× the results (6.06 M) and 2.8× the advisories, and costs 9% of throughput. It is compared only against the carry-forward oracle.

The two semantics-preserving encoding and filtering variants act on the source, the stage #24 identified as the busiest.

### Watermark bound and live latency (08 November from 09:00, p4)

| Run | Measured results | Queueing p50 / p95 / p99 ms | Output latency p50 / p95 / p99 ms | Watermark wait p99 ms | TM cores |
|---|---|---|---|---|---|
| 1x slice | 9,854 | 194 / 245 / 246 | 15,253 / 167,228 / 277,191 | 1,020 | 0.04 |
| 10x slice | 9,469 | 151 / 220 / 221 | 1,710 / 11,341 / 28,060 | 129 | 0.18 |
| 100x | 323,875 | 184 / 283 / 293 | 369 / 2,116 / 3,175 | 151 | 0.28 |
| 100x, 60 s bound | 323,789 | 193 / 252 / 265 | 958 / 2,707 / 3,663 | 605 | 0.27 |
| 300x | 274,113 | 153 / 237 / 262 | 231 / 833 / 1,205 | 52 | 0.44 |
| 1000x | 199,750 | 145 / 220 / 238 | 190 / 362 / 572 | 19 | 1.20 |

Means over 3 repeats. The standard deviations are in [tables.md](tables.md).

- **Queueing stays flat at every rate.** Queueing is the job's own delay behind the readiness model, the only stage a setting of the job controls. It was 145 to 194 ms at p50 and 220 to 283 ms at p95 from 1x to 1000x. This is consistent with Flink's 200 ms periodic watermark emission plus idleness checks.
- **Output latency falls with rate.** At low rates it is dominated by `windowWait`: the rest of the five-minute window, which is real time divided by the replay rate. That is set by the feed, not the system.
- **Watermark bound:** the 60 s bound adds 589 ms at p50 compared with 1 s at 100x. That is 60 s of event time divided by 100, plus alignment. The output did not change: both passed their oracle at that bound with 0 late events.
- **Fewer measured results at 1000x:** at 1000x the paced day lasts about 50 s, so the 25 s warm-up excludes a larger share of results.

## Left out, with reasons

| What | Why |
|---|---|
| Parallel stacks to save time | Measured −31% interference (above). |
| p16 on one TaskManager as a result | 2 of 3 repeats ran out of heap with the image's default memory. Reported, with the 2-TaskManager run as the usable p16 point. Raising TaskManager memory was not tried: it would change the allocation that every other run shares. |
| Partitions beyond 16, parallelism beyond 16 | 16 logical CPUs, and throughput already falls above p4. |
| Input rates above about 1.3 M rec/s (preload) or about 1.04 M rec/s (live) | One replayer's ceiling. The harness runs one replayer, so the job's live saturation point was not reached; its preload rate is the measured ceiling. |
| Whole-day live at 1x and 10x, full-week live | 13.4 h and 80 min of wall time per repeat. The 3 M-row slices (09:00 to 09:16:42) cover them. |
| Checkpointed state bytes | Checkpointing was off, as D-35 decided for bounded jobs. State is reported as open windows and peak heap per TaskManager. |
| CPU profile of the TaskManager | Not taken. It would separate fetcher, decompression and parsing cost inside the source. |
| Hot-key-aware partitioning, warm-up tuning | Optional follow-ups by #11's scope. Not changed in the baseline. |
| Multi-host runs | #12. |

## Reproduce

From the repository root with the images built (`docker compose --profile tools build`). The harness takes over Compose project `trading-trends`.

```bash
python3 scripts/validation/issue11/make_configs.py
setsid nohup python3 scripts/validation/issue11/orchestrate.py oracles scale lanes-host scale-2tm > /dev/null 2>&1 &
bench/.venv/bin/python scripts/validation/issue11/posthoc_correctness.py
MPLCONFIGDIR=$TMPDIR bench/.venv/bin/python scripts/validation/issue11/tables.py
```

`orchestrate.py calibrate` repeats the side-by-side test. It needs the lane overrides in `scripts/validation/issue11/` and runs the `docker` wrapper in `bin/` first on `PATH`. Running the whole matrix takes about 15 hours serially. Live repeats spend about 12 of their minutes exporting `ticks`' price events for the latency analysis.
